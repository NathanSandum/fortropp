# fortropp post-launch todo list

Started 2026-10-19. Things deliberately left out of the first release; none blocks launch.

- [ ] **Enforce the page-view cap.** Decided 2026-11-10: an account may go at most 20% over its plan's page views, a buffer for upselling; at 120% its sites stop serving until the month resets or the user upgrades. Ships only alongside a way to avoid it: a one-time payment to stay online for the rest of the month, without raising the next month's cost, and possibly a challenge in front of sites so fake traffic can't push a site over.
- [ ] **Page-view projections and earlier warnings.** Noted 2026-11-10: the dashboard extrapolates the month's page views linearly and says when an account is on track to pass its cap, possibly days ahead. Whether any warning should fire before 100% is to discuss.
- [ ] **Review writing off unpaid invoices.** Decided 2026-11-10: at launch, the invoice left unpaid when an account's websites are deleted for non-payment is written off, so the same account can run up another unpaid month. Review once there's real data; the alternative is keeping it owed, with Home's plan step asking for it before any plan, Starter included. Another option (user's idea): after a write-off, the account gets a flag requiring upfront billing, shown to the user as something like "This account has gained a flag to require upfront billing. Ask support for more information." It may be easy, and is less discouraging when re-onboarding than asking for past debts.
- [ ] **Look into `.well-known` routes.** Noted 2026-11-10: `.well-known` is a standard (RFC 8615) for fixed paths that clients and third-party integrations look up automatically. Find which ones fortropp should serve on `fortropp.dev`, and whether users' sites need to serve any of their own, for example for third-party domain verification. Candidates to check include `security.txt`, `change-password`, OAuth and MCP metadata (one exists: `oauth-authorization-server`), and agent-readable docs (`skills`, `llms.txt`).
- [ ] **Review what happens when a dependency is down.** Raised 2026-11-10 (user): review each outside dependency (Stripe, Postmark, Cloudflare, DigitalOcean) for what its failure does to users, and whether any path should degrade or retry instead of failing.

- [ ] **Proxy arbitrary HTTP methods.** Decided 2026-10-19 in the item 17 review: the worker answers `501 Not Implemented` to any verb outside GET, HEAD, POST, PUT, PATCH, DELETE and OPTIONS (the `worker` crate maps unknown verbs to `GET`, `worker-0.8.7/src/http.rs`, so the flow reads the raw verb from `req.inner().method()`). To proxy WebDAV and custom verbs: the flow's method carries the verb for anything outside the closed set (Rocq `MOther` with a string), proxy rules forward it as-is, files still answer 405, and the interpreter builds the upstream fetch with `web_sys::RequestInit`, since `worker::Method` can't name other verbs.
- [ ] **Proxy WebSockets.** Decided 2026-10-19: proxies strip hop-by-hop headers including `Upgrade`, so WebSocket handshakes reach the upstream as plain requests. Supporting them means forwarding the upgrade deliberately (the runtime's `fetch` with `Upgrade: websocket` returns a `WebSocket` to pair with the visitor's), with its own tests.
- [ ] **Off-provider Postgres backups and restore drills.** Decided 2026-10-22, moved post-launch 2026-10-24: launch relies on DigitalOcean managed Postgres alone (daily backups, 7-day point-in-time restore); the only risk left is losing the DigitalOcean account or provider. Then: a small `backup` container on the backend droplet (inside the VPC; DigitalOcean extensions can't write to object storage and managed backups can't be exported) runs a nightly `pg_dump | age -r <public key>` upload to `fortropp-prod-backups`, with a read-only database role and its own bucket token; the bucket has an R2 lock (~30 days) and lifecycle expiry (~35 days), both in OpenTofu, and likely the Infrequent Access storage class (large, written nightly, read only in drills or disasters; check its 30-day minimum against the ~35-day expiry); the age private key lives offline (password manager + paper). Restore drills: restore both the managed backup and the dump into a scratch database on a schedule and check the result; alert when the nightly dump fails or goes missing. Design details in `production_notes.md` §8.
- [ ] **Least privilege per component.** Raised 2026-10-22: each piece needs little (worker reads; backend presigns uploads and downloads, lists, deletes on site/account deletion and pruning), so a security mistake in one should have a small blast radius. Limits found so far: an R2 binding gives the worker full access to its bucket (it only reads by convention); R2 tokens are per bucket but only read or read/write (no write-only, delete comes with write); Cloudflare API tokens for KV are likely account-wide, not per namespace (to verify). Options to weigh: splitting deletion/pruning into a separate job with its own credentials, signed manifests and routing records (`todo_list.md` Misc), and per-purpose Cloudflare API tokens (KV, custom hostnames).
- [ ] **Separate kinds of delete by time: retention on the site bucket.** Decided 2026-10-22. A site's backups are its earlier deploys, sharing content-addressed blobs with the live one, so a separate backup bucket would double every blob. Instead: an R2 bucket lock on `fortropp-prod-enam` (blobs and manifests) so a buggy or compromised backend can't destroy history within the window, and deletion (pruning, site/account deletion) becomes expiry through lifecycle rules. Invariants to keep until then:
  1. Never overwrite a key: blobs and manifests stay write-once.
  2. Deletion stays one small code path, so it can move to its own job with its own credentials.
  3. Privacy policy (blank today, needed before launch) promises deletion "within N days", never "immediately", to leave room for the retention window.
- [ ] **Public Suffix List entry for `fortropp.app`.** Decided 2026-10-22: PRIVATE section, submitted once fortropp serves thousands of users (smaller projects are likely declined). Needs a `_psl` TXT record linking the PR and the registration extended to more than 2 years past the PR date. Gives each `<site-id>.fortropp.app` its own cookie scope. Before submitting, confirm the own-domain reservation still holds once every `x.fortropp.app` parses as an apex, and update the `psl` crate.
- [ ] **Forward `CF-Access-*` headers on proxy rules.** Noted 2026-11-01: `serve-core/src/forward.rs` drops every visitor-sent header starting with `cf-`, so `CF-Access-Client-Id`/`CF-Access-Client-Secret` never reach an upstream protected by Cloudflare Access, and it refuses the request. Read from the code, not tested. Kept for now (user): nobody needs it yet, and sending those secrets from a browser would be unusual. If someone does, exempt that prefix from the strip and test it on real Cloudflare first.
- [ ] **A central budget for Cloudflare API calls.** Raised 2026-11-02 (user): encode "we never break the account-wide API limit" in the codebase and ration calls as we approach it, instead of each caller being careful. Cloudflare's limit (about 1,200 requests per 5 minutes per account, per item 14; verify) is shared by custom hostnames, KV and anything else on that account. Likely shape: one type that is the only way to reach the Cloudflare API, tracking usage in Redis, with priorities, so writes a user waits on (registering, routing) proceed while optional calls (the re-validation `PATCH` from Check, status reads) get shed first and degrade softly. Relates to item 14, which lowers the volume. The pre-launch version is much smaller: two Redis limits on the `PATCH` from Check, one per domain and one across all domains, past which Check only reads.
- [ ] **`www.<root>` shares the root's admission.** Moved post-launch 2026-11-09 (user); the model is to be redesigned from scratch, an attempt on 2026-11-09 was discarded. Goal: `www.<root>` is free exactly when `<root>` would be, proof stays per name. Until then, users who only want `www.<root>` can also add `<root>`, whose umbrella admits `www` without proof; whether and how to tell them is a wording decision.
- [ ] **A fixed IP as the root-domain fallback for providers without ALIAS.** Moved post-launch 2026-11-09 (user). ALIAS to the domain's `<label>.edge.fortropp.app` stays the default; the setup dialog would show an A record only behind a link like "Provider doesn't offer ALIAS? (GoDaddy and others)". Likely host: Fly.io; the IP must stay stable for years, and certificates issue only for domains claimed on fortropp. Recheck Chromium's HTTPS-RR issue (40257146) before building any forwarding.
- [ ] **A failed state for root domains that never finish setup.** Decided 2026-11-09 (user): the origin-override loop handles root domains newest first, contacting Cloudflare for at most 30 domains a round, so abandoned ones only wait for later rounds. After a few days to a week pending (to decide), move the domain to a failed state, release its override, and email the user with the likely cause sorted into kinds (no DNS record found, record pointing elsewhere, certificate validation failing), so the email says what to fix.
- [ ] **IPv6 for the origin override.** Decided 2026-11-08: while a root domain is pending, its `<label>.edge.fortropp.app` override points at the droplet with an A record only. Add an AAAA record from a tofu `ORIGIN_IPV6` output, created and deleted with the A record, once the IPv6 path is tested: a request over IPv6 to port 80 is aborted and the challenge path answers 404. Untested so far, and a broken path with an AAAA record could fail challenges for checkers that prefer IPv6.
- [ ] **Deleting versions (high priority).** Without it, a user at the storage limit can be soft-locked: kept versions hold blobs the user can't free. Any version can be deleted except head, live and previewed. The versioning model is in `todo_archive.md`.
- [ ] **Seamless updates for old dashboard tabs.** Beyond the launch toast, e.g. SvelteKit's `pollInterval` with a hard reload on the next navigation (earlier suggestion, not settled).
- [ ] **Can a real user act before the page hydrates?** Moved post-launch 2026-11-09 (user). Check auth forms on a throttled connection. If input is lost, the fix is progressive enhancement, a product decision.

- [ ] **Failed site creation orphans its blobs in R2.** Moved post-launch 2026-11-09 (user). `Website::create` (`backend/src/models/website.rs`) writes the scaffold's blobs and manifest to R2 mid-transaction, so a failure before commit rolls back the rows and leaves the objects. Also: the preview route goes to KV after the commit, so a KV failure returns an error for a website that exists, and a retry makes a second one.

- [ ] **Replace, append or unset a header per subtree in `[[headers]]`.** Moved post-launch 2026-11-09 (user): safe after the v1 freeze only as an addition (new keys, no change to what existing configs mean). Each block says, per header name: replace (`values`), `append = [...]`, or `unset = [...]`. Blocks apply least to most specific. A name in both lists is an error; `append` needs a value in `values`; `unset` must not have one. Append joins with `, `. `Set-Cookie` is never comma-joined. Touches `site-config`, the schema, docs, `ReplyHeader`, and the Rocq model and corpus.
